## 第一步：为什么做，遵循什么原则

### 1.1 为什么做

**公司层面：BizBase 底座。** 公司里销售、运营和开发都在用 AI 做应用，以后还会有 GEO 之外的业务线。界面和功能重复可以接受，真正的麻烦是每个应用各存一份客户、各建一套账号和权限：同一个客户在两个系统里对不上，离职的人在某个应用里还能看数据，一个客户能看到另一个客户的东西。BizBase 要解决的就是这件事：客户、合同、服务、人员、权限和基本业务动作只有一份，所有应用通过同一套身份和授权读写它们（已确认，D-003、E-01）。成功的标志不是 App 或表的数量，而是新应用接进来时不用再造一份主数据和权限。

**当前业务线：GEO 运营。** 公司 2025 年 8 月开始做 GEO，早期全包：资料、文案、投放、采集、分析、再优化。客户和问句增多后，工作靠加人，方法散在个人电脑和个人 skill 里，采集口径各不相同，投放成本和回链没有回收，用户描述为“接单增长而亏损加重”（用户陈述，未做财务核算）。合同按问句、平台和期间考核 Top3 等指标，客户会拿原始记录复核，所以测量结果必须可信、可追溯、口径说得清。GEO 运营 App（`geo_operations`）承载这条业务线的专属对象和规则，客户与合同复用 ERPNext，用户与角色复用 Frappe（已确认，D-016、D-018）。

**为什么先做签约后服务流程。** 用户的原话是“当前最主要的目标是接到客户之后，把整个流程跑通”（已确认，D-017）。已有签约客户在服务中，考核结果直接关系交付和结算，而测量和考核目前最缺统一口径。获客、线索、售前诊断、内容生成和投放在业务流程上排在前面，但线索已在飞书表格汇集，内容和投放有现成小组和工具在做，开发上可以放后。没有可信的测量，后面内容和投放做得好不好也无从判断，所以测量链是其他环节的基础。

**为什么从一开始就支持客户侧组织自管。** 实际签约形态已经出现：总部先签、子公司后来直签；渠道先签、终端客户后来直签；集团还可能要把子公司 A 的产品 A 和子公司 B 的产品 B 合在一起看（D-018、D-030）。授权模型如果等客户登录时再补，每张表、每个查询、每个导出都要返工，而返工期间最容易出现越权。客户多了以后，由公司替每个客户建账号、改角色也不可持续。所以数据模型和权限从第一个对象起就按多层客户组织设计，客户登录界面可以后上（Agent 推荐，待确认；D-030 范围）。

**为什么从一开始就支持 CLI 与 Agent 操作。** 采集程序和报告 Agent 本来就是程序调用；运营的大量工作（录问句、换词、查指标、取数写报告）也适合交给 Agent。公司的主要风险是权限不一致：如果 Agent 只能靠管理员账号或直连数据库来用这套系统，它就会绕过行级权限，造成的问题正是 BizBase 要消除的。所以人在后台能做的业务操作，都要有对应的 API、CLI 和 Agent skill，并且受同一套权限约束（已确认，D-029）。每加一个业务操作就同时加它的能力编码，比事后补一整套开放接口便宜得多。

### 1.3 边界

**开发顺序靠后（已确认，D-017）：** 获客品牌、线索接入与分配、售前拓词与诊断、内容生成、投放执行、SOP 启动清单。线索继续在飞书表格汇集。回链导入在签约后服务流程中预留，能按客户查到发了哪些文章和链接。

**模型现在设计，界面以后上线（D-030；上线时点为 Agent 推荐，待确认）：** 客户登录、客户侧用户与角色自管、组合视图。D-017 规定近期不做客户登录。

**只保存不分析（已确认，D-028）：** 情绪分析近期不做；采集程序拿到的商品卡原样保存，以后需要时重算。

**只记事实不算钱（已确认，D-023）：** 销售与运营分成、违约金、投放费用分摊。规则由用户提供后再做计算。

**不在本项目范围：** 采集程序本身是独立系统，本项目只定义任务领取与结果回传的 API（D-020）；jkstone 只参考思路，不接入、不依赖（D-029）；移山 ID 登录由另一会话开发，是否作为员工统一身份在第三步作为候选列出，本计划不依赖它。

**需要另行授权：** 生产发布、生产数据迁移、权限扩大、付费投放、写入他人系统（D-004）。测试客户的真实资料只存在本地预览环境和私有目录，不进 Git（D-017）。

### 2.1 整体完成的判断

以下全部成立，才算项目整体完成：

1. G1 至 G14 都能用真实记录或标明的测试用例重复验证，不靠演示数据。
2. 跨应用、跨入口的身份和事实一致：同一客户、合同、服务在后台、看板、CLI、Agent 和其他应用里查到的是同一份。
3. 权限一致：同一个人通过任何入口能做的事相同；隔离类验收（G2、G7、G10、G11、G12）在每个版本都回归通过。
4. 历史可解释：任何一个过去的数字都能查到当时的口径、名单和原始记录。
5. 新应用可接入：一个新应用从拿到凭证到完成第一次获授权查询，不需要改动底座。

不以 App 数量、DocType 数量或仓库合并数量衡量完成。

## 第五步：之后如何循环

前四步确认后不再整体重做，也不再为每一轮单独写五步（D-031）。之后只循环第五步：

```mermaid
flowchart LR
    A["从 delivery-map 队列取下一个行动"] --> B["补当次的模型变化与验收用例"]
    B --> C["实现：Build 与 geo_operations"]
    C --> D["交付到 8080 frontend"]
    D --> E["按验收用例实际操作"]
    E --> F["复盘：发布记录与新发现"]
    F --> A
```

1. **取。** 从 [delivery-map.md](delivery-map.md) 的队列取最前面一个未完成行动。
2. **补。** 只写这一次的模型变化（新增或修改的对象、字段、状态、权限、能力编码）、验收用例和实现方式。需要用户决定的事集中一次提出，已确认的目的、原则和成果不再追问。
3. **交付。** 部署到 8080 本地预览 `frontend` 站点，可访问、可操作才算交付（D-004）。
4. **验收。** 按验收用例实际操作；隔离与权限类用例每次回归；本次新增的后台操作，同时检查对应的 API、CLI 能力是否可用并受同样权限约束（D-029）。
5. **复盘。** 留发布记录（问题、提交、入口、验收结果、已知限制、回退方式）。新想法放进 opportunities 或队列末尾，不打断当前行动；未通过验收就如实记为未发布。
6. 再取下一个。

**开发节奏。** 争取每天至少交付一个可用版本：部署到 8080 本地预览、可访问、可操作、通过验收；文档和提交不算交付（D-004）。这是第五步的节奏要求，不是治理原则。

**什么时候修订前四步。** 只有出现影响目的、成果、范围、数据归属或权限的重要新事实时，才局部修订受影响的段落，把修订记入 decisions.md，被修订部分重新请用户确认。日常的取舍、排序微调和实现细节不触发修订。
