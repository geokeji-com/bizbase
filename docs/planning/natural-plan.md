## 第一步：为什么做，遵循什么原则

### 1.1 为什么做

**公司层面：BizBase 底座。** 公司里销售、运营和开发都在用 AI 做应用，以后还会有 GEO 之外的业务线。界面和功能重复可以接受，真正的麻烦是每个应用各存一份客户、各建一套账号和权限：同一个客户在两个系统里对不上，离职的人在某个应用里还能看数据，一个客户能看到另一个客户的东西。BizBase 要解决的就是这件事：客户、合同、服务、人员、权限和基本业务动作只有一份，所有应用通过同一套身份和授权读写它们（已确认，D-003、E-01）。成功的标志不是 App 或表的数量，而是新应用接进来时不用再造一份主数据和权限。

**当前业务线：GEO 运营。** 公司 2025 年 8 月开始做 GEO，早期全包：资料、文案、投放、采集、分析、再优化。客户和问句增多后，工作靠加人，方法散在个人电脑和个人 skill 里，采集口径各不相同，投放成本和回链没有回收，用户描述为“接单增长而亏损加重”（用户陈述，未做财务核算）。合同按问句、平台和期间考核 Top3 等指标，客户会拿原始记录复核，所以测量结果必须可信、可追溯、口径说得清。GEO 运营 App（`geo_operations`）承载这条业务线的专属对象和规则，客户和合同需要能关联到实际服务；按 P2 的本地实测结果，设计上优先复用 ERPNext 的 Customer 和 Contract，不把本地通过当成生产验收。

**为什么先做签约后服务流程。** 用户的原话是“当前最主要的目标是接到客户之后，把整个流程跑通”（已确认，D-017）。已有签约客户在服务中，考核结果直接关系交付和结算，而测量和考核目前最缺统一口径。获客、线索、售前诊断、内容生成和投放在业务流程上排在前面，但线索已在飞书表格汇集，内容和投放有现成小组和工具在做，开发上可以放后。没有可信的测量，后面内容和投放做得好不好也无从判断，所以测量链是其他环节的基础。

**为什么从一开始就支持客户侧组织自管。** 实际签约形态已经出现：总部先签、子公司后来直签；渠道先签、终端客户后来直签；集团还可能要把子公司 A 的产品 A 和子公司 B 的产品 B 合在一起看（D-018、D-030）。授权模型如果等客户登录时再补，每张表、每个查询、每个导出都要返工，而返工期间最容易出现越权。客户多了以后，由公司替每个客户建账号、改角色也不可持续。所以数据模型和权限从第一个对象起就按多层客户组织设计，客户登录界面可以后上（D-030、D-032；不在此承诺上线日期）。

**为什么从一开始就支持 CLI 与 Agent 操作。** 采集程序和报告 Agent 本来就是程序调用；运营的大量工作（录问句、换词、查指标、取数写报告）也适合交给 Agent。公司的主要风险是权限不一致：如果 Agent 只能靠管理员账号或直连数据库来用这套系统，它就会绕过行级权限，造成的问题正是 BizBase 要消除的。所以人在后台能做的业务操作，都要有对应的 API、CLI 和 Agent skill，并且受同一套权限约束（已确认，D-029）。每加一个业务操作就同时加它的能力编码，比事后补一整套开放接口便宜得多。

### 1.3 边界

**开发顺序靠后（已确认，D-017）：** 获客品牌、线索接入与分配、售前拓词与诊断、内容生成、投放执行、SOP 启动清单。线索继续在飞书表格汇集。回链导入在签约后服务流程中预留，能按客户查到发了哪些文章和链接。

**模型现在设计，界面以后上线（D-030、D-032；具体上线日期未定）：** 客户登录、客户侧用户与角色自管、组合视图。D-017 规定近期不做客户登录。

**只保存不分析（已确认，D-028）：** 情绪分析近期不做；采集程序拿到的商品卡原样保存，以后需要时重算。

**只记事实不算钱（已确认，D-023）：** 销售与运营分成、违约金、投放费用分摊。规则由用户提供后再做计算。

**不在本项目范围：** 采集程序本身是独立系统，本项目只定义任务领取与结果回传的 API（D-020）；jkstone 只参考思路，不接入、不依赖（D-029）；移山 ID 登录由另一会话开发，是否作为员工统一身份在第三步作为候选列出，本计划不依赖它。

**需要另行授权：** 生产发布、生产数据迁移、权限扩大、付费投放、写入他人系统（D-004）。测试客户的真实资料只存在本地预览环境和私有目录，不进 Git（D-017）。

## 第二步：完成后是什么样

**成果画面已完成，作为第三步头脑风暴的依据。** 到一次双周复盘时，运营选中服务和期间，能说明：合同承诺了什么、实际采到了什么、按当期口径表现怎样、哪些证据还缺。客户质疑某个问句在某个平台的前三提及率时，运营能用同一批原始记录重算这个数；销售不需要再拿另一张表对数字。看板回答“现在怎样”，报告解释“这一期怎样、与上期能否比较、下一期准备做什么”。

下面是项目级目标，不是当前已交付能力，也不是首个版本要一次做完的清单。“近期”指签约后的服务流程，“后续”包括对客开放和更多业务接入。以 C1（对外服务）和 C2（公司自身，走普通合同流程）验证真实业务；跨客户复用、越权等不会自然发生的情形用标明的测试数据验证。P2 决定这些事实放在哪里，不改变这里的验收结果。

| G12 | 后续（模型近期） | 集团用户 | 把子公司 A 的产品 A 和子公司 B 的产品 B 组合成一个视图查看；口径不同的指标分开列出，不强行合并。 | 同一测试组织：组合视图的计数等于两个单独视图之和，比率按计数重新算；撤销对子公司 B 服务的授权后，组合视图里 B 的数据立即消失。 |
| G13 | 后续 | 其他业务线与同事做的应用 | 获客到签约（线索、售前诊断到合同）、内容与投放（含回执、回链与费用）、经营与分成（费用、退款、贡献事实）陆续接入同一底座，复用同一套客户、合同、服务、身份、凭证和权限，不另建客户表和权限体系。 | 每条后续业务线上线时，至少一个独立应用通过凭证接入；跨应用查询同一客户和服务结果一致；越权请求被拒；未知费用显示为未知，不计为零。 |
| G14 | 持续 | 平台维护者 | 知道谁在何时通过哪个入口做了什么；每天的版本都能验证、能回退，数据不因升级丢失。 | 每个版本留发布记录（问题、提交、入口、验收结果、已知限制、回退方式）；至少演练一次从备份恢复；审计记录覆盖后台、CLI、Agent、采集程序四种入口。 |

**复盘时的两个走查例子（G3–G6）。** 同一问句今天在平台 A 漏采、在平台 B 已采待分析，运营可分别定位采集缺口和分析积压，昨天的回答标出实际日期。双周报发出后若收到迟到样本或出现排名改判，复核人员可对照已交付版本和修订结果，看到各自采用的回答、判定理由及分母。同一次回答重分析只占一个样本。

**续约与渠道转直签的历史可见性（G11、G12 补充验收，推荐规则，待确认）。** 历史记录保留原合同、服务与采样口径，不复制到新合同。客户查看某一期，取决于当前用户是否仍有该期服务、标的和材料的读取授权，不取决于今天由谁签约。

- **同一客户续约：** 对继续服务的标的，续约时明确列出获准沿用的历史范围。仍有旧期读取权的成员可在同一看板切换两期，时间线上标出合同分界；新一期新增的标的或人员不因此自动获得旧期权限。跨期可见不等于指标可比。
- **渠道转直签：** 用同一终端组织建新合同，不改写旧期签约方。终端客户原有且仍有效的历史权限保留；若旧期只有渠道获权，直签本身不补授旧期权限。按原约定核准后，可只开放该终端特定产品、期间和材料。原渠道不会因曾经签约而看到新直签期；旧期只在原授权仍有效时可见。
- **怎么验：** 用终端成员、渠道成员两个账号分别查旧期、新期，再撤掉一项历史授权。看板、组合指标、原文附件和导出均随授权收窄，不删历史记录；无权查看的样本不进汇总或对比的分母。

D-003 的六类成果在新画面中的位置：销售与运营数据对得上 → G1、G13；新应用能接入获授权数据 → G9、G10、G13；交付证据可追溯 → G4、G5、G6、G8；客户或渠道只看到授权内容 → G7、G11、G12；成本与经营事实可核对 → G13 与下文基线指标；版本可验证可恢复 → G14。

### 2.1 整体完成的判断

以下全部成立，才算项目整体完成：

1. G1 至 G14 都能用真实记录或标明的测试用例重复验证，不靠演示数据。
2. 跨应用、跨入口的身份和事实一致：同一客户、合同、服务在后台、看板、CLI、Agent 和其他应用里查到的是同一份。
3. 权限一致：同一个人通过任何入口能做的事相同；隔离类验收（G2、G7、G10、G11、G12）在每个版本都回归通过。
4. 历史可解释：任何一个过去的数字都能查到当时的口径、名单和原始记录。
5. 新应用可接入：一个新应用从拿到凭证到完成第一次获授权查询，不需要改动底座。

不以 App 数量、DocType 数量或仓库合并数量衡量完成。

**贯穿各场景的验收条件（2026-11-19）。** 审批、审计、防错填与防误操作、安全、性能都纳入成果验收。从第一个涉及相应操作的版本起验证，后台、API、CLI 和 Agent 同样适用。下表是推荐的验收方式，不代表功能已经实现或审批岗位已经确定。

| 要求 | 业务人员能观察到的结果 | 怎么验 |
|---|---|---|
| 审批：控制高影响变更，不让日常录入排队 | 普通草稿可直接保存；向新组织开放历史资料时，明确展示接收方、产品、期间和材料，指定的有权人员批准后才生效。 | 用渠道转直签样例：提交不等于授权；拒绝后新范围仍不可见；批准后只开放批准的范围。申请人修改范围须重新审批，不能沿用原批准。 |
| 审计：能还原一次决定 | 有权复核的人能查到谁发起、谁批准、通过哪个入口、何时生效、改前改后是什么；机器调用可追到凭证标识，不记录密钥明文。 | 抽一笔历史授权和一次批量换词，不靠询问经办人即可还原经过；普通业务用户不能改写审计记录。 |
| 防错填、防误操作：写入前指出问题 | 反向日期、错配的客户与产品由服务端拒绝，提示具体字段或导入行；格式正确但影响大的操作，在生效前展示影响范围。 | 导入时混入一行其他客户的产品；在界面和 API 都拿到可纠正的错误，该行未写入。预览换词能看到影响哪些计划和生效日期；重复提交同一操作不产生第二次变更。 |
| 安全：所有入口都守同一授权边界 | 授权检查覆盖列表、详情、聚合、导出及私有附件；机器凭证只拥有工作所需能力。 | 用两个组织的测试账号核对同一份材料：未授权一方拿不到正文、附件或汇总数字；撤权后，已保存的视图与旧链接也不能用于重新读取。已合法下载的副本不承诺远程收回。 |
| 性能：忙时仍能完成日常工作 | 在约定的数据量、并发数和时间窗下，运营能切换看板、翻页和查看证据；大批量导出时，采集仍能领取任务并按时回传。 | 记录负载、P95 响应时间、任务积压和漏采。以看板切换 ≤1.5 秒、列表分页 P95 ≤500 毫秒作初始预算；用代表性负载实测，再确定正式目标，不把空库成绩当作达标。 |

## 第五步：之后如何循环

前四步确认后不再整体重做，也不再为每一轮单独写五步（D-031）。之后只循环第五步：

```mermaid
flowchart LR
    A["从 delivery-map 队列取下一个行动"] --> B["补当次的模型变化与验收用例"]
    B --> C["实现：Build 与 geo_operations"]
    C --> D["交付到 8080 frontend"]
    D --> E["按验收用例实际操作"]
    E --> F["复盘：发布记录与新发现"]
    F --> A
```

1. **取。** 从 [delivery-map.md](delivery-map.md) 的队列取最前面一个未完成行动。
2. **补。** 只写这一次的模型变化（新增或修改的对象、字段、状态、权限、能力编码）、验收用例和实现方式。需要用户决定的事集中一次提出，已确认的目的、原则和成果不再追问。
3. **交付。** 部署到 8080 本地预览 `frontend` 站点，可访问、可操作才算交付（D-004）。
4. **验收。** 按验收用例实际操作；隔离与权限类用例每次回归；本次新增的后台操作，同时检查对应的 API、CLI 能力是否可用并受同样权限约束（D-029）。
5. **复盘。** 留发布记录（问题、提交、入口、验收结果、已知限制、回退方式）。新想法放进 opportunities 或队列末尾，不打断当前行动；未通过验收就如实记为未发布。
6. 再取下一个。

**开发节奏。** 争取每天至少交付一个可用版本：部署到 8080 本地预览、可访问、可操作、通过验收；文档和提交不算交付（D-004）。这是第五步的节奏要求，不是治理原则。

**什么时候修订前四步。** 只有出现影响目的、成果、范围、数据归属或权限的重要新事实时，才局部修订受影响的段落，把修订记入 decisions.md，被修订部分重新请用户确认。日常的取舍、排序微调和实现细节不触发修订。
