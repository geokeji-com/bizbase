# BizBase 首轮整体规划

日期：2026-11-18。用户以“整体规划认可，两项接受”确认本规划；流程、成果与发布定义分别见 [D-002、D-003、D-004](../cycle/decisions.md)。这是整体基线，不是已完成的数据模型或发布结果。

本次集中完成自然式规划的前四步，形成长期基线；后续用 ratchet 管理第五步的实施行动。整体规划与实施轮次分别编号，避免把规划文档算作一个软件版本。

## 第一步：为什么做，以及遵循什么原则

用户明确的目标：让不同岗位持续制作应用时，可以复用一致的数据、权限和基本业务能力；支持当前 GEO 和后续业务线。允许不同界面和重复功能，不以统一所有人的工作台为目标。[依据 E-01](../cycle/evidence.md)

预期业务价值：减少重复录入、跨系统核对和追问交付的时间；提高交付可追溯性，并为真实成本和人员贡献提供可核查依据。收益目前未测量，不承诺未经验证的节省比例。

成果基线的原则（D-003）：

- 同一业务事实有可识别的身份、来源和修改责任；可以有多个展示与缓存。
- 同一身份并不自动拥有所有客户权限；数据访问随实际授权关系生效。
- 历史承诺、输入、规则和结果能解释；当前配置不能无提示地改写过去。
- 先验证和复用现有能力；新建部分写明缺口。现有材料和实现都允许被证伪。
- 数据缺失、失败、未知如实呈现；界面完整不能替代真实业务链完整。

上述原则随整体规划获接受；具体数据结构、迁移和不可逆业务规则在触及它们的实施轮次单独裁决。

## 第二步：完成后会是什么样

以下为目标场景，不是现在已经实现的能力。场景中的“同一服务”须落到真实业务记录，不能靠名称相同或演示数据验收。

| 谁在使用 | 完成后的成果画面 | 如何证明 |
|---|---|---|
| 销售与运营 | 各自应用中的客户、优化标的、服务范围能对上；有差异能追到来源和责任方 | 同一真实服务在至少两个独立应用中交叉核对 |
| 普通同事开发新应用 | 按接入示例取得获授权数据，复用业务动作，无须再维护一份孤立客户和权限体系 | 一个独立示例应用完成身份、范围、查询及拒绝场景 |
| 运营负责人 | 查到某服务的采样证据、分析口径、文章版本与发布回链，并识别缺口 | 至少一条真实交付链逐项追溯至来源 |
| 客户或渠道 | 只能看到被明确授权的服务和材料；对外展示口径有依据 | 对客功能上线前验证越权、分享及撤权场景 |
| 经营负责人 | 能区分合同承诺、执行事实、发布费用、退款与待核实成本 | 选定服务与原始单据核对；不把未知费用计为零 |
| 平台维护者 | 能知道谁在何时通过哪个应用做了什么；新增版本可验证、可恢复 | 调用审计、接口兼容、升级及恢复记录 |

整体完成的判断：跨应用身份和事实一致、授权一致、历史可解释、新应用可接入；上表真实场景可重复验证。不是以 App 数量、数据表数量或仓库合并数量衡量完成。

待测的经营指标：重复录入次数、核对耗时、交付材料准备耗时、发布回链完整率、新应用接入时间。首个可用版本留存基线后，再约定改善幅度。
