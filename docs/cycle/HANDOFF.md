## 2. 用户真正要解决什么

BizBase 是公司共同的数据、权限和基本业务能力底座。GEO 是第一条业务线，后续可能还有其他产品。销售、运营和开发人员都能借助 AI 制作应用，因此功能重复可以接受，**不同系统的数据隔离、身份混乱、权限不一致才是主要问题**。

用户允许质疑竞对说法、口述、SOP、已有仓库和我们之前的方案。它们都是证据或候选，不是不可修改的真理；优先找真实业务对象、真实关系和真实使用结果。

六类成果已获认可：销售与运营的数据对得上；新应用能接入获授权数据；交付证据可追溯；客户/渠道仅看到授权内容；成本与经营事实可核对；版本可验证、可恢复。详见已确认的 [natural-plan.md](../planning/natural-plan.md)。

## 3. 用户讲述的 GEO 业务要点

以下是用户业务陈述，尚未逐项核对真实合同与生产数据。完整梳理和候选建模在 [geo-service-model.md](../business/2026-11-17-geo-service-model.md)。

1. **业务演变**：2025 年 8 月开始 GEO，早期全包完成资料、文案、投放、采集、分析、再优化；客户和问句增加后依赖堆人、成本不透明，个人工具和流程分散。
2. **自营获客**：一个主品牌、五个子品牌，各官网兼具留资和自有信源作用；公司自身也使用 GEO 优化获客。
3. **线索与销售**：官网、小红书、抖音、微信服务号、400、活码等汇集线索；可通过 API 或人工录入。自动接入与自动分配是两回事，已有销售归属应保留。跟进后形成意向，由销售主导、运营参与沟通。
4. **售前与签约**：依据行业、品牌、产品拓词，重视指数、搜索联想等可解释证据；做广范围售前诊断后协商服务问句，签约、启动会、整理客户资料，再优化。用户也说过“授权诊断”，是否为独立授权环节尚未确认。
5. **多方关系**：签约方、被服务组织、优化标的可以不同；总部/分公司、渠道/终端客户不能全部简化成同一种父子关系。优化标的可以是公司、品牌、产品。
6. **采样条件**：监测是探针采样，不掌握 AI 平台全部真实搜索量。保留平台、App/网页/API、Chat/Work、联网、思考、深搜/强度等条件。频率可能是每日/每周、指定时段每小时、随机或均匀采样。
7. **排名与分析**：准确术语是 **Top 5、Top 3**，早期 Top 50/300 为转述错误。维护目标名称、别名和竞品集合；按问句→监测任务→整体聚合。分析策略、模型和版本影响结果；分母、权重、名单外实体是否占名次等未定。
8. **证据与信源**：保留提示问句、回答、信源列表、分享链接和截图。信源有文章、视频、商品卡片；涉及去重、跳转、404、补标题/正文。“AI 厂商缓存导致 404”仅为推测。
9. **内容与投放**：分析引用率及薄弱问句，从词根、意图、场景生成内容；现有小组通过聚合平台自动投放并回收链接。用户希望集中基本能力；实施前先核验可复用的现有生成/投放系统。
10. **报告与变更**：报告经历 Excel→JSON/HTML→周报/双周报/跨期报告→客户看板。存在换词、暂停、年框每三个月换词；竞品、策略、模型变化不能无提示改写历史结果。合同、采样、分析、报告、结算周期分别表达。
11. **经营规则**：销售分成、运营分成、考核时点、投放费用分摊尚需真实规则和样例，不自行设比例、达标起算或暂停顺延逻辑。
12. **SOP 边界**：模板要求不等于客户已完成；发送不等于确认，事实准确性确认不等于公开授权，提交投放不等于上线、取得回链或复采达标。

## 5. Build、App、Site、API：保持概念一致

- **Build**：Frappe 自带的构建工作区，入口 `/desk/build`。可进入 DocType、表单定制、报表、工作区和脚本等原生工具；不是独立安装的业务 App，也不是 Frappe Builder 建站产品。
- **Site**：一套站点及数据库/配置/用户。多个 App 可装在同一 site；并非每个 App 都要单独建 site。共享数据库不代表不同 App 的业务对象已合并，也不代表所有用户共享访问权。
- **App**：版本化功能包，可保存标准 DocType 定义、配置、代码和迁移。Build 与代码可以配合；D-014 已在原站点安装空 App，Build 继续作为开发入口，不新建实例。
- **配置持久化**：站点自定义记录与开发模式下导出到 App 的标准定义有不同发布方式；使用前按当前模式核对备份/导出，不把所有界面修改说成自动进入 Git。D-014 已启用本站点开发模式并挂载 App 源码；具体操作见 App README。
- **API**：Frappe/ERPNext/CRM 已有原生 API，无须把已有能力全部重写。外部独立项目可以通过 API 使用本站点；公司特有业务契约或跨对象规则再扩展。认证、角色与具体客户/服务授权分别验证，自定义 API 本身不天然安全，原生入口也需符合约定边界。
- **两套 CRM**：ERPNext CRM 与独立 Frappe CRM 使用不同业务记录；同 site 不会自动混成一张线索表，配置集成才会产生关联/同步。隐藏菜单只是界面取舍，不等于卸载模块、释放其全部资源或完成数据治理。原 ERPNext CRM 未因本次撤回被拆除。
