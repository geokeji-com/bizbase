# 国内 GEO 服务链与数据对象调研

调研日期：2026-11-17。范围：国内服务商、监测工具及 AI 平台的一手公开资料。本文用于帮助 BizBase 建立候选业务模型，不代表本公司的实际流程已确认，也不是供应商采购建议。

## 结论

公开产品资料中可以辨认出两类供给：一类提供诊断、策略、内容和分发的持续运营服务；另一类提供问题采样、答案分析和报告工具。两者需要关联的数据有交集，承担的交付责任不同。不能仅用一张“客户表”或一个“曝光分数”覆盖整个 GEO 业务。

对 BizBase 更有价值的建设方向，是让客户、品牌、服务范围、问题版本、内容版本、发布事实和监测证据能够相互追溯。以下先记录厂商公开描述，再给出独立的建模建议；未登录厂商后台、未购买服务、未验证其宣传效果。

## 对国内平台差异能确认到哪一步

百度智能云检测页的**搜索索引全文**列举 DeepSeek、豆包、Kimi、腾讯元宝、通义千问和文心一言，并描述有限问题集、单次采样、失败/超时不进入评分分母等规则。[官方 URL](https://cloud.baidu.com/experience/geo-check) 本轮直接打开该页只取得包含“GEO 检测”入口的页面骨架，因此这些细则属于官方 URL 的索引证据，**没有在当前可见页面或真实检测中独立核实**，不能据此承诺该服务当前行为。它们仅作为候选口径参考。

“答中有我”官方明确其采样走 API，API 回答与 C 端手机应用/网页回答存在差异，提供联网模式与人工抽检校准。其产品页还披露不同平台通过不同 API 接入；其中具体一致性百分比、模型版本及 API 新功能均未由本轮向模型厂商逐项复核，因此不作为平台事实或能力保证。[产品接入说明](https://da.sekahui.com/product/)、[常见问题](https://da.sekahui.com/faq/)

据此建议：平台名称不能单独确定一种观测口径。至少还要记录采样通道（网页、移动端、API 等）、具体模型或产品版本（能取得时）、联网状态、地区/语言、账号/上下文条件、采样时间和重复序号。未知条件应存为未知，不能默认为各批次相同。

## 候选对象与关系：供下一轮业务访谈验证

下表是面向 BizBase 的设计推断，不是厂商内部数据库结构，也未对当前 Frappe 创建任何 DocType。

| 对象 | 记录什么 | 为什么要独立 |
| --- | --- | --- |
| 客户组织 `CustomerOrganization` | 购买服务的主体及与其他系统的标识映射 | 客户可能管理多个品牌；品牌名称不能直接充当合同主体 |
| 品牌 `Brand`、被测产品/服务 `MarketOffering` | 被监测和被优化的市场对象及别名 | 同一个客户不同品牌、产品、地区可能有不同问题与目标；与本公司出售的 GEO 服务产品分开 |
| 服务约定 `ServiceAgreement` | 合作范围及约定的交付/验收口径 | 协议状态不能直接决定所有工作或监测状态 |
| 服务实例 `ServiceEngagement` | 某次约定实际服务的品牌、范围、团队和有效期间 | 同客户可以有多次、并行或跨业务线服务；不要只在客户上放一个“服务中”开关 |
| 服务周期 `ServicePeriod` | 某次阶段/周期的范围、基线、报告与验收 | 周期长度及暂停/续约规则待公司确认；不预设一律自然月 |
| 问题集及版本 `PromptSetVersion` | 题目、意图分类、平台/地区范围、纳入验收与否 | 改题会改变指标意义；历史报告必须指向当时的问题集 |
| 品牌事实与证据 `BrandFact` / `Evidence` | 主张、原始依据、来源、有效期、审核结果 | 内容应用可复用同一事实，避免各生成工具各编一套品牌信息 |
| 内容资产及版本 `ContentVersion` | 文案或其他资产、所依据事实、审核状态 | 编辑草稿不能覆盖历史已发布的版本 |
| 发布记录 `Publication` | 内容版本、渠道/账号、外部 URL、提交与实际上线时间、状态 | 一份内容可多渠道发布；提交成功不等于上线或被模型引用 |
| 交付任务 `DeliveryTask` | 负责人、动作、关联对象、产物及验收 | “发了多少篇”与“效果怎么样”分别记录，便于协作和复盘 |
| 监测批次/单次采样 `Run` / `Observation` | 采样计划、每个问题每次回答、状态、时间与通道 | 超时、拒答、重试、有效但未提及是不同事实 |
| 分析结果 `AnalysisResult` | 基于哪个回答、哪个解析版本得出的提及、推荐、情绪等 | 原始答案保持不变；重新解析和人工修正需可追溯 |
| 引用 `Citation` | 回答中的 URL、域名、出现位置与归属 | 引用某域名不等于引用了本期发布文章；关联需证据 |
| 报告/验收 `ReportVersion` / `Acceptance` | 所用数据范围、指标版本、结论、反馈及验收时间 | 同期多个报告要可复算；报告完成不等于客户验收 |

建议关系：客户组织关联品牌与服务实例；服务实例关联具体服务范围和周期；周期关联任务、问题集版本和报告；发布记录指向内容版本；每个采样指向问题版本和运行条件；分析与引用指向采样证据。品牌归属变更、一个品牌是否允许多个客户共享，以及服务中断规则，需要业务解释后才能确定关系基数。

## 指标口径需要明确的七件事

以下是依据上述采样差异提出的统计设计建议，不是对任一厂商公式的复制。

1. **分母**：计划样本、尝试样本、有效回答分别计数。采集失败单列；拒答是否纳入有效样本由指标定义决定，不可运行时临时改。
2. **事件**：提及、正向推荐、首个出现、排名第一、引用官网是不同事件。答案先出现品牌名，不一定是在推荐该品牌。
3. **重复采样**：同题每次运行都保留原始记录；重试不要重复增加正式统计权重。批次应披露每题每平台的有效次数。
4. **比较条件**：问题集、平台集合、地区语言、采样通道、时间窗发生变化时，报告标注不可直接同比，或同时输出可比子集。
5. **品牌识别**：别名、缩写、同名品牌、产品名及人工修正使用版本化规则，避免解析器更新被误认为营销效果变化。
6. **汇总权重**：按回答平均、按题平均、按平台平均会产生不同结果。应保存公式版本、分子/分母和权重，不能只有一个“可见度分”。
7. **效果归因**：内容上线、被引用、被提及、点击、线索和成交是不同观测。发布后指标上升只能先记录关联；要声称带来成交，需要接入实际流量/线索数据并明确归因窗口。

## 能力建设优先级

建议先统一可追溯数据，允许上层工具提供各自的内容工作台、监测看板和客户报告。最小可复核链路为：

`服务范围 → 问题集版本 → 单次采样证据 → 分析版本 → 指标结果 → 报告版本`

若公司实际提供内容代运营，再将 `品牌事实 → 内容版本 → 审核 → 发布记录 → 引用证据` 接入同一条链。合同、计费、暂停、服务周期与验收规则，等业务介绍后决定复用 ERPNext 对象还是新增业务对象。

## 本轮没有确认的事项

- 没有确认本公司的实际服务产品、收费方式、人员分工、平台覆盖、采样规模及交付 SLA。
- 没有验证供应商后台权限、API 可用性、数据导出完整性或实际客户案例效果。
- 没有把官网的客户 Logo、奖项、融资、效果数字作为供应商能力排名。
- 新榜、慧辰部分入口及 AIDSO 页面直取失败；它们不是本文结论的证据，不根据二手榜单补充推断。
- 本文不假定服务商能控制模型推荐。下一轮应先对照实际合同、报告、任务及采样记录，再决定对象、状态与验收口径。
